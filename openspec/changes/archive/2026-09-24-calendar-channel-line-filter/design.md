## Context

See proposal.md - Why. Relevant current code, all in `apps/mobile/src/`:

- `views/CalendarPage.vue` renders its channel visibility filter below `.cal-grid` (originally the read-only `.cal-legend`), and separately renders `<CouponFilterToolbar>` below the "Active on {date}" heading for status/discount/sort only.
- `utils/calendar.ts`'s `getDayChannelLines(days, coupons, channels, enabledChannelKeys)` and `filterDayListCoupons`'s `DayListFilters.channelFilter: Set<string>` both take the resolved set of channel keys currently shown.
- `components/CouponFilterToolbar.vue` renders a single-select ("radio") row of channel chips (`'all'` + one button per channel, `.chip.on` styling) at the top, above the sort/status/discount-type toolbar. It's shared between `CodesPage` (channel row shown) and `CalendarPage`'s day-list toolbar (channel row hidden via `showChannelFilter="false"`, since Calendar's channel filter lives below the grid instead).
- `stores/coupons.ts`'s `channelFilter: 'all' | string` and `db/queries/coupons.ts`'s `CouponListFilter.channelKey?: string` back the Codes list's single-select channel filter with a real SQL `WHERE`, unlike Calendar's in-memory filtering over an already-loaded coupon array.

**Revision (second round of feedback, after the first round above had already shipped):** two further requests arrived once the multi-select Calendar filter was in place and being used:
1. Selecting every channel individually (one by one) should collapse back to the same state as "All" — "All" highlighted, every per-channel chip unhighlighted — not stay as N individually-highlighted chips with "All" unhighlighted, even though the two states show the same coupons/lines.
2. The Codes list's own channel filter should work identically to Calendar's — multi-select, "All" default, same collapse-to-"All" behavior — reversing this design's original Non-Goal of leaving it untouched.

This section (and the Decisions below) documents the design as revised for both rounds together, since by the time of the second round the first round's specifics (single-select Codes, Calendar-only scope) were superseded rather than still applicable.

## Goals / Non-Goals

**Goals:**
- Replace the read-only channel legend with an interactive multi-select channel filter, gating both the grid's per-day lines and the selected-day list.
- Give the Codes list's channel filter the exact same selection semantics as Calendar's (multi-select, "All" default, collapse-to-"All" when every channel ends up individually selected) — sharing the actual toggle/resolve logic between them via a small pure-function util, not just parallel implementations that happen to agree.
- Keep the "empty selection / collapse-to-empty" *state representation* free of app-specific meaning (SQL vs. in-memory) — the shared util operates on plain `Set<string>`s and a count, so it works identically whether the caller resolves it into a SQL `IN (...)` (Codes) or an in-memory filter over an already-loaded array (Calendar).

**Non-Goals:**
- Persisting either channel filter across visits or app restarts (out of scope — Calendar's mirrors the existing, non-persisted `dayListStatusFilter`/`dayListDiscountTypeFilter`; Codes' channel filter was never persisted either, same as its status/discount-type filters).
- A shared *markup* component for the two chip rows beyond what's needed for them to look and behave identically (see Decision 8) — they still live in different places in each screen's layout (Codes: top of its toolbar; Calendar: below the grid), which stays a deliberate difference, not something this revision changes.

## Decisions

**1. `dayListChannelFilter` changes from `ref<string>('all')` to `dayListSelectedChannels = ref<Set<string>>(new Set())` — a positive whitelist of explicitly selected channel keys, empty by default.**
Why a whitelist, and why empty-by-default rather than pre-populated with every channel key: this mirrors the exact convention `dayListStatusFilter`/`dayListDiscountTypeFilter` already use elsewhere in this same component — "empty selection ⇒ no restriction, show everything" — rather than inventing a second, opposite convention (a disabled-set, considered and superseded; see below) for just this one filter. It also matches the requested interaction directly: "All" is selected exactly when nothing else is, and selecting any specific channel immediately deselects "All" — which falls out for free when "All" `on` state is simply `dayListSelectedChannels.size === 0`, with no separate mode flag to keep in sync.
Initialization timing matches the existing filter refs: set once at component creation (their factory default), not reset on every `onIonViewWillEnter` — so, like today's `dayListStatusFilter`, switching tabs away and back preserves whatever the maker last selected, only a full remount (app relaunch, or the tab being destroyed/recreated) resets it to empty ("All"). A channel created via `ChannelManagerModal` while Calendar is already mounted is a pre-existing edge case (Calendar's local filter state was already not reactive to newly-created filter *options* appearing mid-session for status/discount-type, which have a fixed value set); with an empty-selection-means-all convention, a brand-new channel is included in "All" automatically and needs no special-casing, the same as it would be for status/discount-type if those ever gained new values at runtime.

**2. (Superseded during implementation feedback — kept for history.) An earlier pass of this design tracked *disabled* keys instead, so a channel defaulted to visible without needing `channelsStore.items` to have loaded yet.**
That shape was replaced by Decision 1's plain whitelist after implementation feedback asked for exactly the status/discount-type "empty ⇒ show all" convention, including the specific interaction where selecting one channel deselects "All" and selecting no channels reverts to it. The disabled-set version could represent that too, but only by layering an extra "is this a fresh/untouched state" concept on top — the whitelist gets it as the direct, literal reading of `size === 0`. The async-loading concern doesn't reappear: `enabledChannelKeys` (see Decision 3) falls back to "every current `channelsStore.items` key" whenever the whitelist is empty, so it's correct however many channels have loaded so far, before or after `channelsStore.load()` resolves.

**3. `getDayChannelLines` gains a fourth parameter, the effective enabled-channel set, and filters `channels` down to it before computing `weekChannelOrder`.**
Concretely: `getDayChannelLines(days, coupons, channels, enabledChannelKeys: Set<string>)` — the existing `channels.filter((channel) => weekActiveKeys.has(channel.key))` line becomes `channels.filter((channel) => weekActiveKeys.has(channel.key) && enabledChannelKeys.has(channel.key))`. This is what makes a deselected channel's slot disappear (not just render blank) — it's excluded from `weekChannelOrder` entirely, so it never reserves a stacking position for that week, matching the spec's "Per-day channel indicator lines" requirement's deselected-channel scenario. Passing `enabledChannelKeys` as a `Set<string>` (rather than reusing `ChannelRow[]` prefiltered by the caller) keeps `activeChannelKeysOn`'s unrelated logic untouched and makes the filter's effect visible at the one call site that needs it. This parameter's signature is unchanged by the Decision 1/2 revision — only what `CalendarPage` computes and passes into it changed.
`CalendarPage` derives the *effective* enabled set from the whitelist with a fallback to "everything" when nothing is selected: `const enabledChannelKeys = computed(() => dayListSelectedChannels.value.size === 0 ? new Set(channelsStore.items.map(c => c.key)) : dayListSelectedChannels.value)`. This is the one place the whitelist's "empty means all" convention gets resolved into a concrete set of keys; every downstream consumer (`getDayChannelLines`, `filterDayListCoupons`) only ever sees the resolved set, never the raw whitelist or an "is this All mode" flag.

**4. `filterDayListCoupons`'s `DayListFilters.channelFilter` field is the same resolved `Set<string>` from Decision 3, and its check stays `coupon.channel !== undefined ? !filters.channelFilter.has(coupon.channel.key) : false` — a coupon is excluded only if it has a channel and that channel is absent from the resolved set.**
This half of the contract is unaffected by the Decision 1/2 revision: `filterDayListCoupons` never sees "selection is empty" as a distinct state, only the already-resolved set of channels currently being shown (every channel, when the maker hasn't narrowed to specific ones). A coupon with no channel (its only channel was deleted) is never excluded by this filter, same as it's never excluded by the Codes list's own channel filter today.

**5. (Superseded by Decision 8 below — kept for history.) The interactive channel toggle row was first added as new markup inline inside `CalendarPage.vue`, reasoning that a shared component wasn't worth it for a single consumer.**
That reasoning held only as long as Codes' channel filter stayed single-select and out of scope. Once the second feedback round asked for Codes to behave identically, there were two real consumers wanting the exact same selection UI, and duplicating the markup and CSS into both `CouponFilterToolbar.vue` and `CalendarPage.vue` would have been the actual premature-abstraction mistake in the other direction — two copies that could silently drift apart the next time either needs a tweak, for a UI that's now supposed to be identical by requirement, not by coincidence. See Decision 8.
`CouponFilterToolbar.vue`'s `showChannelFilter?: boolean` prop (default `true`) is unaffected by this revision — it still governs whether that toolbar renders a channel-filter row at all, which stays `false` for Calendar's usage (its channel filter still lives below the grid, not in this toolbar) and `true` for Codes'.

**7. Selecting every channel individually collapses the selection back to empty ("All"), via the same shared toggle function every caller uses — not a special "is everything selected?" check layered on top afterward.**
Concretely, in `utils/channelSelection.ts`:
```ts
export function toggleChannelSelection(current: Set<string>, key: string, totalChannelCount: number): Set<string> {
  const next = new Set(current)
  if (next.has(key)) next.delete(key)
  else next.add(key)
  return next.size >= totalChannelCount ? new Set() : next
}
```
Folding the collapse into the toggle itself (rather than, say, a separate `computed` that swaps in an empty set when `selected.size === channels.length`) means there's exactly one moment where "did this toggle just complete the full set?" is decided, and every caller (Codes, Calendar) gets it automatically just by routing every channel-chip click through this function — there's no second place that could disagree about when the collapse should happen. `>=` rather than `===` tolerates `totalChannelCount` being stale by the time a click resolves (e.g. a channel was deleted elsewhere a moment ago) without ever under-collapsing.
A companion, `resolveSelectedChannelKeys(selected: Set<string>, allKeys: string[]): Set<string>`, resolves the "empty means All" convention into a concrete key set for callers that need one up front (Calendar's in-memory filtering does; Codes' SQL query doesn't — see Decision 8).

**8. The Codes list's channel filter is rebuilt on the same `Set<string>` (empty ⇒ "All") model as Calendar's, all the way down to the DB query layer, and both screens' chip rows render through one new shared component, `ChannelFilterChips.vue`.**
- `stores/coupons.ts`: `channelFilter: 'all' | string` becomes `channelFilter: Set<string>` (default empty). `setChannelFilter(filter)` (which took the single resolved value) becomes `setChannelFilter(next: Set<string>)` (takes the already-toggled set) — the store itself doesn't need to know about the toggle-and-collapse rule; whoever calls it (see below) already resolved that via `toggleChannelSelection`. `load()` passes `channelKeys: this.channelFilter.size === 0 ? undefined : [...this.channelFilter]` to `listCoupons`.
- `db/queries/coupons.ts`: `CouponListFilter.channelKey?: string` becomes `channelKeys?: string[]`; the existing join-then-`inArray(coupons.id, ...)` shape is unchanged except the inner `where(eq(channels.key, filter.channelKey))` becomes `where(inArray(channels.key, filter.channelKeys))`, gated on `filter?.channelKeys?.length` instead of `filter?.channelKey`. The SQL layer never needs an explicit "resolve empty to every key" step the way Calendar's in-memory path does — "no `channelKeys` condition added" already means "no restriction" at the SQL level, which is exactly what an empty/undefined selection should mean.
- `CodesPage.vue` (not the store) computes the toggle: `toggleChannelFilter(key)` calls `couponsStore.setChannelFilter(toggleChannelSelection(couponsStore.channelFilter, key, channelsStore.items.length))`, and a `selectAllChannels()` calls `couponsStore.setChannelFilter(new Set())`. This keeps the toggle util's `totalChannelCount` argument sourced the same way in both places it's needed (`channelsStore.items.length`, read directly by whichever component is handling the click) without `stores/coupons.ts` importing `useChannelsStore` itself — `stores/channels.ts` already imports `useCouponsStore` (to refresh the coupon list after a channel deletion), so the reverse import would be a real circular module dependency between the two store files, not just a style preference.
- `ChannelFilterChips.vue` (new, in `components/`): takes `channels: ChannelRow[]` and `selected: Set<string>`, emits `toggle: [string]` and `select-all: []`, and renders the "All" + per-channel chips exactly as Calendar's row already did (same `filter-chip`/`channel-chip`/`on` classes, same per-channel `--chip-color` styling, same dot swatch) — this is the one place that markup and its CSS live now. `CouponFilterToolbar.vue` renders it (wrapped in its existing `.chip-row`/`channel-extra`-slot layout) when `showChannelFilter` is true, wired to its own `channelFilter`/`toggle-channel`/`select-all-channels` props/emits; `CalendarPage.vue` renders it directly in place of its former inline chip markup, wired to `dayListSelectedChannels`/`toggleDayListChannel`/`enableAllDayListChannels`. Both `toggleDayListChannel` (Calendar) and `toggleChannelFilter` (Codes) call the same `toggleChannelSelection` from Decision 7, so the two screens' collapse-to-"All" behavior isn't just visually consistent, it's the same function call.

**6. "All" and the per-channel chips share one mutually-exclusive-looking, but actually just derived, highlight rule: `on` is `dayListSelectedChannels.size === 0` for "All", and `dayListSelectedChannels.has(channel.key)` for a channel chip.**
Activating "All" sets `dayListSelectedChannels.value = new Set()` unconditionally (clearing any specific selection), which is what makes every per-channel chip lose its highlight in the same click, and every channel's lines/coupons show again — matching the requested "selecting All deselects everything else and shows everything" behavior exactly, with no separate mode flag to keep in sync with the selection set. Selecting a specific channel while "All" is active doesn't need to explicitly "turn All off" either — it's a natural consequence of `dayListSelectedChannels` becoming non-empty, which is the only thing "All"'s highlight reads. Deselecting the last individually-selected channel (clicking it again with nothing else selected) has the same emergent effect in reverse: the whitelist becomes empty, so "All" is highlighted and everything is shown again — this is the intended behavior (equivalent to activating "All"), not a special case that needs its own code path, and matches how `statusFilter`/`discountTypeFilter` already behave when their last selected value is deselected.

## Risks / Trade-offs

- [With an empty-selection-means-all whitelist, there is no user action that shows "nothing" — deselecting the last selected channel, or selecting every channel individually, both snap back to "All" rather than staying at a fully-specific selection] → This is intentional (Decisions 6-7), matching how `statusFilter`/`discountTypeFilter` already behave, and matches the specific behavior requested for both filters. A maker who wants to see only some channels still can; there's no requested path to "show none" or to a visually-distinguished-but-behaviorally-identical "all N individually checked" state.
- [Changing `DayListFilters.channelFilter`'s type, and now also `CouponListFilter.channelKey` → `channelKeys`, are breaking changes to their modules' exported shapes] → Each is confined to its module and the one or two call sites that use it (`utils/calendar.ts` ← `CalendarPage.vue`; `db/queries/coupons.ts` ← `stores/coupons.ts`), so the blast radius is contained to the files actually touched in Decisions 3-4 and 8.
- [Codes' channel filter moving from a single SQL `eq()` to `inArray()` changes its query plan slightly for the common single-channel-selected case] → `inArray` with one element compiles to the same effective condition as `eq` would; SQLite's query planner handles a one-element `IN (...)` without a meaningful performance difference at this app's data scale (a maker's own coupon list, not a shared/multi-tenant table).

## Migration Plan

No data migration. This is a UI/local-state and query-filter-shape change across `CalendarPage.vue`, `CouponFilterToolbar.vue`, the new `ChannelFilterChips.vue`, `utils/calendar.ts`, the new `utils/channelSelection.ts`, `stores/coupons.ts`, `db/queries/coupons.ts`, and `CodesPage.vue`; ship as a normal app update. Rollback is a plain revert, no persisted data shape changes anywhere (nothing here touches SQLite schema, migrations, or Pinia-persisted `localStorage` keys).
