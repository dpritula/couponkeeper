## Context

The delivered pack (`C:\Tmp\CouponKeeper-android-icons.zip`) is a complete, ready-to-drop-in Android resource set — not raw source needing rework. Its colors (`#4C7A5D` background, `#F3EFE4` foreground fill) already match `--ck-sage`/`--ck-paper` in `apps/mobile/src/theme/variables.css` exactly, and its `res/` tree mirrors Capacitor's own generated layout 1:1 (same file names, same density folders). See proposal.md - Why/What Changes for the full list of files being added/replaced.

The app currently has no `drawable-{m,h,xh,xxh,xxxh}dpi` folders at all (only `drawable-land-*`/`drawable-port-*`, used for splash screens) and no `smallIcon` set on any scheduled notification — `LocalNotifications.schedule()` falls through to the plugin's own default, which is why this is additive (new folders) for the notification icon rather than a same-name replacement.

## Goals / Non-Goals

**Goals:**
- Replace every placeholder Android icon asset with the delivered pack's version, using the same file names/paths Capacitor generated so no other resource reference needs to change.
- Make the expiry-warning notification (the app's only current notification type) actually use the new small icon.
- Keep the pack's non-Android-resource files (Play Store icon, SVG sources) in the repo, in a location that makes clear they're design assets, not build inputs.

**Non-Goals:**
- No redesign or re-export of the icon itself — the delivered PNGs/XMLs are used as-is.
- No change to notification content, scheduling, or dedup logic (`coupon-expiry-notifications` spec is unaffected — see proposal.md - Capabilities).
- No iOS icon work (iOS platform isn't added to this repo yet, per CLAUDE.md's Tech Stack).
- No app-icon-badging or dynamic/seasonal icon variants — out of scope, not requested.

## Decisions

**Replace, don't merge, the launcher `mipmap-*`/`drawable-v24`/`values` files.** The pack's `res/` tree uses the exact same paths Capacitor's default generator used (confirmed by diffing against the current `apps/mobile/android/app/src/main/res/` tree), so every file is a straight overwrite — no manifest change needed beyond what's already there (`android:icon`/`android:roundIcon` already point at `@mipmap/ic_launcher`/`ic_launcher_round`, unchanged by this pack).

**Add the pack's `drawable-v24/ic_launcher_monochrome.xml` and reference it from both `ic_launcher.xml` and `ic_launcher_round.xml`.** The current manifest has no `<monochrome>` element (2-layer adaptive icon: background + foreground only); the pack's XML is 3-layer. This is a pure addition — Android versions below 13 ignore the unknown element, so there's no compatibility risk in adding it unconditionally rather than gating it.

**Wire the notification icon via the plugin's per-call `smallIcon` option, not a global manifest default.** `@capacitor/local-notifications` reads `smallIcon` from each `LocalNotifications.schedule()` call's notification object (already confirmed: `buildNotification()` in `expiryNotifications.ts` is the single call site building every scheduled notification, in both the single- and multi-coupon branches). Setting `smallIcon: 'ic_stat_coupon'` there is a one-line, single-call-site change, versus adding new Capacitor plugin config (`capacitor.config.ts`) for a value there's only one call site needing anyway. If the app ever gains a second notification type, that call site should set the same value rather than each duplicating the literal — not worth a shared constant for one call site today.

**Store the non-Android-resource pack files (`ic_launcher-playstore.png`, `source/*.svg`) at `apps/mobile/icon-source/`, not inside `android/`.** Everything under `apps/mobile/android/` is either Capacitor-generated or a direct build input; the Play Store icon and editable SVG sources are neither (nothing in the build reads them). A sibling `icon-source/` directory next to `android/` keeps them discoverable and repo-tracked (so a future icon revision has the original vectors, not just rasterized `res/` output) without implying they're consumed by any build step. `preview.png` (a rendered preview contact-sheet, not a usable asset) is not checked in — it's derivable from the checked-in sources/renders if ever needed again, and keeping it would read as a shipped asset when it isn't one.

**Keep all five densities (`mdpi` through `xxxhdpi`) for both the launcher and notification icons**, matching what the pack provides and what Capacitor's own default generation already covered — no evidence in this repo of a minSdk/density restriction that would make dropping any of them safe, and pruning them isn't something the proposal asked for.

**Favicon: base it on `icon_full.svg`'s art, with a PNG rasterized from `ic_launcher-playstore.png` as the fallback — but cropped, not a verbatim copy (revised after maker feedback; see below).** `icon_full.svg` (already checked into `apps/mobile/icon-source/` from this change's first round) is self-contained — background gradient plus glyph in one 108×108 viewBox — so it needs no extra wrapper or masking to stand alone as a favicon, unlike `foreground.svg` (transparent background, meant to sit inside the OS's own adaptive-icon mask) or `notification.svg` (a single-color silhouette, meant for a status-bar context, not a full-color brand mark). `apps/mobile/public/favicon.svg` and `favicon.png` are derived from it and referenced via a modern `<link rel="icon" type="image/svg+xml">` plus a `<link rel="alternate icon" type="image/png">` fallback for browsers without SVG-favicon support (older Safari).

**Both the favicon and the header logo (below) crop in tighter than `icon_full.svg`'s own 0 0 108 108 viewBox — a maker-feedback round, after the first version shipped with the source's full viewBox and read as too small/padded at both sizes.** `icon_full.svg`'s generous margin around the glyph is Android's adaptive-icon safe zone (icons are authored at 108dp with content kept inside a ~66dp circle, since the OS may mask/crop/zoom the edges into a circle, squircle, teardrop, etc. depending on device/launcher) — necessary for the launcher icon (`icon-source/icon_full.svg` itself is left untouched, still the correct source for that), irrelevant for the favicon and header logo since we render the whole square ourselves with no OS masking involved. The glyph's actual rendered bounding box was measured precisely (not eyeballed) by rendering the SVG in the browser at a known pixel size and reading `getBoundingClientRect()`: ~[24.98, 83.02]×[31.84, 76.16] in the 108-unit viewBox, centered on the same (54, 54) point the source rotates the glyph around. `viewBox="23 23 62 62"` — square (so the background fills edge-to-edge with no letterboxing) and centered on that same point — crops close to that measured box while leaving a small, even margin. The favicon's PNG fallback is cropped to the equivalent pixel box before downscaling (`ic_launcher-playstore.png` is 512×512 for the same 108-unit design, so the crop box scales by 512/108), not just resized, so it matches the SVG rather than reverting to the padded look.

**Header logo: one shared `AppLogo.vue` component, inlining the same (now-cropped) SVG markup, dropped into each header's existing `.brand`/`.brand2` element rather than a new markup block.** Inlining (not an `<img src="...">`) avoids a network request for a tiny, load-bearing piece of chrome and — same reasoning as the self-hosted fonts in `theme/fonts.css` — keeps the app fully offline-capable with nothing fetched at runtime. A shared component (not the SVG markup copy-pasted three times) is the right level of reuse here: CLAUDE.md's existing precedent (`CouponFilterToolbar`) already establishes sharing a small presentational component across screens where the markup would otherwise triplicate; unlike the header's surrounding CSS block (which *is* intentionally duplicated per-screen per CLAUDE.md, since each screen's header has its own independent styling needs today), the logo's actual path data has no reason to ever differ between the three screens, so duplicating it would only create three places a future icon revision could drift out of sync. `.brand`/`.brand2` become `display: flex; align-items: center; gap: 8px` (were block-level text before) so the logo sits inline before the text, with `.brand-logo { width/height: 22px; border-radius: 6px; flex-shrink: 0 }` — the same rounded-square treatment `icon_full.svg`'s flat corners need to read as a "badge" next to text, rather than a jarring hard-edged square. `.brand-logo`'s own CSS block is duplicated across the three files' `<style scoped>` blocks (same reasoning CLAUDE.md already gives for `.brand`'s duplication: `scoped` styles can't be shared across single-file components without a new shared stylesheet, which isn't worth introducing for one small rule).

**The logo mark keeps `icon_full.svg`'s original fixed colors in both light and dark UI theme, matching the Android launcher icon's own behavior.** The Android OS icon never adapts to the app's internal theme setting (light/dark/system) — it's a fixed brand mark, not a themed UI element — and the in-app header logo is explicitly "the same icon, shown somewhere else" per this request, so it follows the same rule rather than being redrawn with `--ck-*` tokens. This does mean the logo's colors are static hex values (`#5B8B6C`/`#3B6249`/`#F3EFE4`, copied from `icon_full.svg`) inside `AppLogo.vue`, the one deliberate exception to this codebase's "carry colors as CSS variables, never hardcode hex" rule (see CLAUDE.md's Design System) — justified because this is a static brand mark, not a UI surface that should follow the app's own palette.

## Risks / Trade-offs

- [The web/`jeep-sqlite` dev server has no Android launcher, recents, or notification-tray surface at all] → This change is only meaningfully verifiable via `assembleDebug` installed on the emulator (`Vichara_API36`, per CLAUDE.md's Getting Started) or a device — check the launcher icon, recents card, and a real triggered/manually-fired expiry notification there before calling this done, not just that the build compiles.
- [`npx cap sync android` overwrites generated `android/` resources from a `cap-generated`-style source if one exists] → Confirmed not applicable here: this repo's `android/` platform was added once and these `res/` files are hand-maintained (no `assets/capacitor.config.json`-driven icon regeneration step in this project), so a plain file replace is safe and durable across future `cap sync` runs. If a future Capacitor tooling change introduces icon auto-generation from a single source image, revisit this.
- [Themed/monochrome icon (Android 13+) can't be visually verified unless the emulator/device explicitly has "Themed icons" enabled in launcher settings, which isn't the default] → Verify by toggling that setting on once during manual testing; don't rely on the default launcher state alone to confirm the monochrome layer works.
- [`AppLogo.vue`'s inlined SVG is hand-copied from `icon_full.svg` rather than imported/generated, and both it and `favicon.svg` use a cropped viewBox rather than the source's own] → If `icon_full.svg` is ever revised, `AppLogo.vue` and `favicon.svg`/`favicon.png` must be updated to match by hand, re-deriving the crop rather than assuming `23 23 62 62` still fits; note this in a comment at the top of `AppLogo.vue` so it isn't missed.
