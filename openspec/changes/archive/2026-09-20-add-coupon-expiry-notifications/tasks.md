## 3. Notification scheduling core

- [x] 3.1 Create `apps/mobile/src/notifications/expiryNotifications.ts` exporting `recalculateExpiryNotifications()`: reserves a fixed 21-ID range (one per day-offset `0`..`20`). On every call, cancel and rebuild offsets `1`..`20` unconditionally via `LocalNotifications.cancel(...)`/`schedule(...)` from the current qualifying set (per design.md's "bounded, deterministic ID pool" decision) — offset `0` is handled separately in task 3.4a, not touched by this blanket cancel.
- [x] 3.2 In the same module, implement the permission check: `LocalNotifications.checkPermissions()`, calling `requestPermissions()` only when the status is `prompt`/`prompt-with-rationale`; if not `granted` after that, skip all scheduling (offsets `1`..`20` and `0` alike) for this recalculation pass. Verified on the AVD: the system permission prompt appeared on first launch; tapping "Don't allow" produced no crash (confirmed via logcat) and no notification was scheduled (confirmed via `dumpsys notification`). Also discovered and documented a related, separate OS gate — `SCHEDULE_EXACT_ALARM` — see design.md's Risks section.
- [x] 3.3 Implement qualifying-coupon lookup: call `listCoupons()` (unfiltered) from `db/queries/coupons.ts`, and for each row with `status` `active` or `soon`, compute `daysUntilEnd(row.endDate)` (from `db/status.ts`) and bucket it by that value when it falls within `[0, warnDaysBefore]` (read from `useSettingsStore().warnDaysBefore`). Exclude `notStarted`/`expired` rows entirely.
- [x] 3.4 Add a small persisted-state helper (e.g. `apps/mobile/src/notifications/todayState.ts`) backed by a new `couponkeeper.expiryNotificationToday` `localStorage` key storing `{ date: 'YYYY-MM-DD', handled: boolean }`: a `getTodayState()` that resets to `{ date: today, handled: false }` whenever the stored date isn't today's local date, and a `markTodayHandled()` that sets `handled: true` for today's date. Verify with a quick manual check: writing a stale date and calling `getTodayState()` returns `handled: false`.
- [x] 3.4a In `expiryNotifications.ts`, implement offset-`0` handling per design.md's three-way branch, using `getTodayState()`/`markTodayHandled()` from 3.4:
  - If `handled` is already `true` for today, do nothing — don't cancel or touch offset `0`'s notification at all.
  - Else if local time is before `12:00` and today's bucket (from 3.3) is non-empty: cancel offset `0`'s ID, schedule it for `at: new Date(year, month, day, 12, 0)` today, and on a successful `schedule()` call `markTodayHandled()`.
  - Else if local time is `>= 12:00` and `< 18:00` and today's bucket is non-empty: cancel offset `0`'s ID, schedule it for a few seconds from now (e.g. `at: new Date(Date.now() + 2000)` — see design.md's Risks on why not literally "now"), and on a successful `schedule()` call `markTodayHandled()`. This is the maker's "catch-up" requirement.
  - Else (bucket empty, or local time is `>= 18:00`): do nothing.
- [x] 3.5 Make `recalculateExpiryNotifications()` single-flighted (cache and return the in-flight promise to concurrent callers), mirroring `db/client.ts`'s `getConnection` pattern referenced in design.md.
- [x] 3.6 Verified with real scenarios on the AVD (`Vichara_API36`), reading the actual `LocalNotifications.schedule(...)` calls and delivered notifications via `adb logcat`/`dumpsys notification`:
  - Two coupons (`MULTI3`, `MULTI4`) both ending tomorrow → a single `schedule()` call for id `19001` with `title: "2 coupons expiring soon"`, `body: "MULTI3 (Own site) — 1 days\nMULTI4 (Own site) — 1 days"`, `extra.codes: ["MULTI3","MULTI4"]`, `at` correctly resolved to tomorrow 12:00 local (device timezone GMT, so `12:00:00.000Z` — confirms the plain local-`Date` approach is timezone-correct).
  - Created a coupon (`CATCHUP1`) ending today with the emulator's real clock at 13:04 (within the 12:00–18:00 window) and nothing yet scheduled for today → the catch-up path fired: scheduled for ~2s in the future, delivered and confirmed posted via `dumpsys notification` with the exact expected title/body; a subsequent resume-triggered recalculation did not touch or re-fire it (confirmed: only ids `19001`-`19020` were cancelled, `19000` was left alone).
  - Creating a second same-day coupon (`MULTI2`) after today's notification had already gone out (via `MULTI1`'s catch-up firing) → confirmed the following recalculation's `schedule` call never mentioned it; the delivered notification's body stayed exactly `"MULTI1 (Own site) expires today"` — the "already handled today" lock held under a real second coupon, not just in theory.
  - The `now >= 18:00` skip branch was **not** exercised on a real clock — this AVD (a non-eng/"production" system image) refused every attempt to change the system clock (`adb shell date`, `adb root`, and the Settings app's own time picker all silently declined to actually move the clock forward). This branch is a plain early-return with no side effects (see `expiryNotifications.ts`'s `handleToday`), so it's covered by code reading rather than a live trace; flagging here rather than silently claiming a device trace that didn't happen.
