## Context

See [proposal.md](proposal.md) for motivation. Relevant existing state:

- `db/status.ts` already exposes `deriveCouponStatus(startDate, endDate, now?)` (status incl. `notStarted`/`active`/`soon`/`expired`) and `daysUntilEnd(endDate, now?)` (signed day count, defined for every coupon regardless of status). `queries/coupons.ts`'s `listCoupons()`/`attachChannels` already re-derive both on every read, never trusting the stored columns (CLAUDE.md).
- `stores/settings.ts` already persists one small setting (`defaultSort`) to its own `localStorage` key with a read-parse-fallback-to-factory-default helper; `theme` follows the same shape. This is the existing precedent for a new `warnDaysBefore` setting.
- `stores/coupons.ts`'s `create`/`update`/`remove` are the only places coupon data changes; `CodesPage.vue`'s `onIonViewWillEnter` is the only current "app re-entered" hook, but it's page-scoped (Codes only) and doesn't fire on OS-level foreground resume the way `@capacitor/app`'s `resume` event does. `@capacitor/app` is already a dependency but currently unused anywhere in `src/`.
- No notification plugin is installed yet. `@capacitor/local-notifications` (official Capacitor plugin, actively maintained alongside `@capacitor/app`/`@capacitor/status-bar` already in use) is the natural fit: on-device scheduled notifications with no backend, matching the app's local-first architecture (CLAUDE.md).
- Android manifest currently declares only `INTERNET`. Android 13+ (API 33) requires the runtime `POST_NOTIFICATIONS` permission for any notification to be shown at all.
- Clarified with the maker before writing this design: notifications repeat daily for every day a coupon remains within the threshold (not just the day it first enters it); multiple qualifying coupons on the same day share one notification; delivery time is 12:00 local; tapping opens the single coupon's detail view, or the Codes list filtered to that day's set when there's more than one.
- Clarified in a follow-up, before implementation started: if a recalculation runs between 12:00 and 18:00 (later widened to 20:00 — see below) local time and today's notification hasn't fired yet (e.g. the app wasn't opened before noon), it SHALL still be shown immediately rather than lost for the day; past the window it's skipped for that day. And once today's notification has gone out, no further notification may be delivered that same day under any circumstances, even if the qualifying set would otherwise change — this supersedes the original "skip offset 0 if its 12:00 time has already passed" decision below, which is now the end-of-window case of the catch-up window rather than the only case.
- **Bugfix round, after a maker report from a real device** (not the emulator): a coupon created with 2 days remaining and a 3-day threshold produced no notification at all, even though it was already within the window and the time was well before curfew. Root cause, and the fix, are documented in the "Bucketing" decision below — the original bucketing scheme put a coupon in exactly one future slot (its own end date) instead of every day from today through its end date, so `handleToday`'s bucket for *today* only ever contained coupons whose end date was literally today. Same report also asked for the catch-up cutoff to move from 18:00 to 20:00, and for the "soon"/"Expiring" status shown across the app to be driven by the same threshold instead of a separate hardcoded 7-day constant — see the new "Single source of truth" decision below.
- **Second bugfix round, same real device, after the first was deployed:** creating a second and third new coupon (each a different code/channel, each also landing inside today's window) produced *no* notification at all — only the first coupon of the day ever got one. Root cause: the original "today" design locked the *entire day* after the first delivery (`handled: true`, checked before touching offset `0` at all), on the theory that "once per day, ever" was a whole-day constraint. The maker's report showed that reading was too strict: recalculating on every created/edited coupon is pointless if a later recalculation can't still produce new output for a genuinely new coupon. The constraint is per-coupon, not per-day — see the reworked "Offset `0`" decision below, and `todayState.ts`'s `deliveredCodes`/`pendingCodes` (replacing the old single `handled` boolean).

## Goals / Non-Goals

**Goals:**
- Recalculate and reschedule notifications idempotently from current data on every trigger, without needing to diff against whatever was previously scheduled.
- Keep the scheduling window bounded and cheap, exploiting the setting's own `0`–`20` cap.
- Degrade gracefully when notification permission is denied, or when the OS clears scheduled alarms out from under the app (e.g. a device reboot) — recover automatically the next time the app is opened, rather than needing new infrastructure to prevent it.

**Non-Goals:**
- No per-coupon individual notifications for coupons discovered together — coupons found by the *same* recalculation still share one notification, grouped (per the maker's original answer). This is no longer "at most one notification per day" overall, though — see the reworked per-coupon lock below, added after a second bugfix round.
- No user-configurable delivery time — fixed at 12:00 local for this change; revisit only if requested later.
- No push/cloud notifications or server involvement — purely local, consistent with the app's local-first design.
- No `RECEIVE_BOOT_COMPLETED` receiver or other manifest work beyond `POST_NOTIFICATIONS` — see the reboot risk below for why this is an acceptable trade-off here.
- No change to `coupons`/`channels` schema. `deriveCouponStatus`'s *mechanism* (how `notStarted`/`active`/`soon`/`expired` and `daysLeft` are computed from the dates) is unchanged — only its `soon` cutoff becomes a parameter instead of a hardcoded constant, per the "single source of truth" decision below.

## Decisions

**Bounded, deterministic notification-ID ranges — `19001`-`19020` for future offsets, `19000` (`PENDING_ID`) for today's not-yet-fired slot, `19100`-`19199` cycling for today's already-delivered batches.** For offsets `1`..`20` (future days), every recalculation unconditionally cancels and rebuilds them from the current qualifying set — safe, since nothing has fired yet for a day that hasn't arrived. This sidesteps ever having to diff "what's currently scheduled" against "what should be scheduled" (the plugin has no cheap bulk-read-back API for that), and correctly clears stale notifications left over from a since-lowered threshold, a deleted coupon, or a coupon whose dates changed. `PENDING_ID` is reserved *only* for content that hasn't fired yet today — freely cancel-and-reschedule-able, since nothing under it has ever alerted the maker. Each already-delivered today-batch instead gets a *fresh* id from the `19100`-`19199` range (see the "per-coupon lock" decision below for why reusing an id across separate deliveries is unsafe) — 100 slots is generous headroom for one day's realistic manual coupon-creation volume; a maker triggering more than 100 distinct notification events in a single day is not a realistic case worth engineering around. Alternative considered: diff-and-patch every offset, including today — rejected as needless complexity for offsets `1`..`20`, where nothing has fired yet and a full rebuild is just as correct and much simpler.

**A persisted "today" state tracks, per coupon code, whether it's been delivered or is still pending — not a single day-level flag.** A new `localStorage` key (`couponkeeper.expiryNotificationToday`, alongside `warnDaysBefore`) stores `{ date, deliveredCodes: string[], pendingCodes: string[], pendingAt: string | null, nextBatchId: number }` (see `todayState.ts`). Every recalculation first checks this: if the stored `date` isn't today's local date, the whole thing resets for the new day. **This replaced an earlier single `{ date, handled: boolean }` shape** — see the "per-coupon lock" decision below for why a whole-day flag was wrong. `deliveredCodes` is the only reliable "already shown" signal available: the plugin's own `localNotificationReceived` event only fires while the app happens to be in the foreground at the moment of delivery, so it can't be trusted to detect a notification that fired while backgrounded. A code is added to `deliveredCodes` at *scheduling* time for a catch-up (imminent) delivery, or promoted from `pendingCodes` once wall-clock time shows the pending slot's `at` has passed — neither is a true "confirmed delivered" signal (the plugin can't reliably provide one), but both are close enough approximations for this purpose.

**Recalculation is coalesced, not just single-flighted.** Two triggers can land close together (e.g. the app resumes right as a coupon save's own recalculation call is still in flight). The original version made `recalculateExpiryNotifications()` cache its in-flight promise and hand that *same* promise to any concurrent caller — safe for avoiding a racing double cancel/schedule pass, but wrong for freshness: a caller whose own new coupon didn't exist yet when the in-flight pass started `listCoupons()` would get back a promise that never actually considered that coupon, with no further pass ever triggered on its behalf. Fixed with a trailing-edge queue: a call arriving while one is in-flight sets a `rerunQueued` flag and still returns the in-flight promise, but `runUntilSettled()` loops and re-runs `doRecalculate()` immediately if that flag got set before the current pass finished — so every trigger is guaranteed to be reflected by *some* pass, not silently absorbed into a stale one already underway. Mirrors `db/client.ts`'s `getConnection` singleton pattern, extended with the rerun loop.

**Qualifying coupons are read fresh via `listCoupons()`, not from `useCouponsStore`.** The store's `items` reflects whatever filters the Codes screen currently has applied, and may not even be loaded yet when a resume-triggered recalculation runs before the maker has visited Codes. The scheduler calls `listCoupons()` (unfiltered) directly. Fetching the full table is consistent with how `CodesPage`/`CalendarPage` already fetch their full coupon sets client-side rather than paging.

**A qualifying coupon is bucketed under *every* day-offset from today through its end date, not just one — a real bug, found via a maker report, corrected here.** The original version computed `k = daysUntilEnd(endDate)` (today's days-remaining) and put the coupon in `buckets.get(k)` only. Since `k` *is*, by definition, exactly "how many days from today until the end date," scheduling offset `k` always lands the notification on the coupon's end date itself — never earlier — regardless of how many days the coupon has actually been sitting inside the warning window. Two consequences, both confirmed on a real device: a coupon that already qualifies today (say `k = 2` with a 3-day threshold) was completely absent from *today's* bucket (today is offset `0`, and only coupons with `k = 0` ever landed there), so it produced no catch-up notification at all; and the one notification it *did* eventually get, when offset `2` fired two days later, was pre-built with `days: 2` baked in from scheduling time — wrong by construction, since two real days will have passed by the time it fires. The fix: for a coupon with today's days-remaining `k` (already confirmed `0 <= k <= warnDaysBefore`), add it to every bucket `0..k`, each entry carrying its own `daysRemaining = k - offset` (so offset `0` shows `k`, offset `k` shows `0` — "expires today" exactly when it should). This is what makes a single recalculation correctly pre-schedule the *entire* remaining run of daily reminders for a coupon in one pass, not just its last day.

**Permission is requested defensively on every recalculation, not just once at boot.** `LocalNotifications.checkPermissions()` is checked first; `requestPermissions()` is only called when the status is `prompt`/`prompt-with-rationale` (never re-prompting after an explicit `denied`, matching platform convention — Android itself suppresses the dialog on repeat calls once truly denied, so this is safe to call unconditionally). If permission isn't `granted` after that, the recalculation still runs its unconditional cancel step (covers the case where permission was revoked after previously being granted) and then returns without scheduling anything — no persistent in-app nagging UI is added for a denied state (minor scope decision; can be revisited later if it turns out to matter).

**Delivery time uses plain local `Date` construction, not the plugin's `on: {hour, minute}` repeating-schedule form.** Each day's notification is a one-shot `schedule.at: Date`, not a recurring schedule, because its *content* differs from day to day as the qualifying-coupon set changes — a repeating notification can't vary its body per occurrence. `new Date(year, month, day, 12, 0)` already resolves against the device's local timezone (including DST), so no manual offset math is needed. Offsets `1`..`20` always target `(today + offset days) at 12:00 local` — always in the future, no special casing needed.

**Offset `0` (today), per-coupon lock: reworked after the second bugfix round.** The original design locked the *entire day* after the first delivery (a single `handled: true` flag, checked before touching offset `0` at all) — a maker report showed this silently swallowed every coupon created after the first one that day, directly contradicting "recalculates on every created/edited coupon." The fix moves the lock to `deliveredCodes`/`pendingCodes` (per-coupon, from the previous decision), computed fresh each recalculation:
1. If a `pendingCodes`/`pendingAt` slot exists and `now >= pendingAt`, promote it: move those codes into `deliveredCodes`, clear the pending slot (its notification has almost certainly fired by now).
2. Self-heal `pendingCodes`: drop any code no longer present in today's freshly-computed bucket (it was edited or deleted out of the window before its pending slot fired) — reschedule `PENDING_ID` with the trimmed content if anything changed, or cancel it if nothing's left pending.
3. `newEntries` = today's bucket minus `deliveredCodes` minus (post-self-heal) `pendingCodes` — the coupons genuinely not yet covered by anything today.
4. If `newEntries` is empty, stop (steps 1-2 already handled any state change needed).
5. If `now < noonToday`: merge `newEntries`' codes into `pendingCodes`, set `pendingAt = noonToday`, cancel-and-reschedule `PENDING_ID` with the *combined* pending content (old + new) for `at: noonToday`. This is what lets several coupons discovered across one morning still coalesce into a single noon notification, rather than each getting its own.
6. Else if `now < 20:00` (the catch-up window): schedule a *fresh* id from the `19100`-`19199` range for `newEntries` only, at a few seconds out, and add those codes straight to `deliveredCodes` (imminent delivery, optimistically treated the same as confirmed — same reasoning as the previous decision). Deliberately a **new** id, not `PENDING_ID` and not a previously-used delivered-batch id: Android notifications carry `ONLY_ALERT_ONCE`, which can silently suppress the sound/heads-up for an *update* to a still-visible notification sharing an id — reusing an id across two separate same-day deliveries risked the second one arriving silently. A fresh id every time sidesteps the question entirely rather than relying on undocumented cross-version behavior.
7. Else (`now >= 20:00`): today's window has closed for `newEntries` — leave them uncovered (neither delivered nor pending); they're reconsidered fresh whenever they still qualify on a later day.

**The "soon"/"Expiring" status threshold is no longer a separate hardcoded constant — it *is* `warnDaysBefore`, read live, everywhere status is derived.** `db/status.ts`'s `deriveCouponStatus` used to have its own internal `SOON_THRESHOLD_DAYS = 7`, entirely independent of this change's notification setting — so a maker could set "warn me 3 days before" for notifications while the "Expiring" badge on every card kept using a fixed, unrelated 7-day cutoff. Per a maker follow-up, these are now the same number: `deriveCouponStatus` takes `soonThresholdDays` as a required parameter (no default — every caller must pass the live value, so a stale hardcoded number can't quietly come back), and its three call sites in `queries/coupons.ts` (`attachChannels` — the read path every screen goes through, plus `createCoupon`/`updateCoupon` for the initial insert value) all pass `useSettingsStore().warnDaysBefore`. Since `CodesPage`, `CalendarPage`, and the detail modals all render whatever `attachChannels` (via `listCoupons` → `toViewModel`) produces, fixing that one call site propagates everywhere without touching any view code — genuinely a single source of truth, not three independently-synced copies. Alternative considered: keep a separate `soonThresholdDays` setting distinct from `warnDaysBefore` — rejected per the maker's explicit ask for one shared value, and because two independently-tunable "how many days is 'soon'" numbers is exactly the confusing duplication being removed.

**Tap routing carries the qualifying codes on the notification itself, not via a re-query.** `schedule()`'s `extra: { codes: string[] }` stores exactly which coupons were included. A single `localNotificationActionPerformed` listener (registered once, alongside the `@capacitor/app` `resume` listener, in a small notifications bootstrap module invoked from `main.ts`) reads `extra.codes` and routes by its length:
- One code → navigate to `/tabs/codes?openCode=<code>`. `CodesPage` gains a route-query check (on mount / `onIonViewWillEnter`) that, when `openCode` is present, looks the coupon up (`getCouponByCode`, converted via `toViewModel`) and opens `CouponDetailModal` for it directly, then clears the query param via `router.replace` so re-entering Codes normally doesn't reopen it.
- More than one code → navigate to `/tabs/codes?notifyCodes=<comma-separated codes>`. `CodesPage` detects this and calls a new `couponsStore` action that loads exactly those coupons (see next decision), showing a small dismissible banner ("Showing coupons from a notification — ×") above the list; dismissing it (or navigating away and back) returns to the normal filtered/sorted view.

**`CouponListFilter` gains an optional `codes?: string[]` field, and `useCouponsStore` gains a separate, transient "notification view" instead of overloading the existing channel/status/discount-type filters.** Reusing the existing filter fields to express "exactly these codes" isn't expressible with them (they filter by attribute, not by an arbitrary set of codes), and repurposing them would also clobber whatever filters the maker had already set on the Codes screen. Instead: `listCoupons` passes `codes` through as `inArray(coupons.code, filter.codes)` (mirroring how `channelKey` is already resolved to an `inArray` condition), and `useCouponsStore` gets a small piece of state (e.g. `notificationCodes: string[] | null`) that, when set, is layered on top of a call to `listCoupons` without disturbing `channelFilter`/`statusFilter`/`discountTypeFilter`. Clearing it (the banner's ×) simply reloads normally with the maker's existing filters intact, exactly as before the notification tap.

**New i18n section `notifications.*`** holds the title/body templates: a single-coupon body (code, channel, days remaining) and a multi-coupon body (a short summary line plus one line per coupon), plus the Settings stepper's label. Exact copy is finalized during implementation, matching the existing terse style of `codes.*`/`status.*` strings.

## Risks / Trade-offs

~~[Android 12+ (API 31+) restricts *exact* alarms behind a separate permission (`SCHEDULE_EXACT_ALARM`)...]~~ **Resolved, not just accepted — third bugfix round, after a real-device screenshot of the "Alarms & reminders" settings screen.** The original assumption ("avoid requesting exact-alarm access") turned out to require an explicit opt-out that hadn't been used yet: `@capacitor/local-notifications` 8.3.1's `LocalNotification` payload has an `isExactNotification` field, defaulting to `true` — that default, not some unavoidable plugin behavior, is what was launching `android.settings.REQUEST_SCHEDULE_EXACT_ALARM` (`Settings$AlarmsAndRemindersAppActivity`) on every `schedule()` call made without the permission. Setting `isExactNotification: false` on every notification this app schedules (in `buildNotification`) makes the plugin skip the permission check and the settings prompt entirely, unconditionally using `AlarmManager.setAndAllowWhileIdle()`/`set()` (confirmed by reading `LocalNotificationManager.kt`'s `setExactIfPossible`). This isn't a compromise: the app never needed to-the-minute delivery — "a convenient time once a day" was always the ask — so inexact scheduling is exactly the right behavior, not a fallback. Verified on-device with `SCHEDULE_EXACT_ALARM` explicitly denied (`adb shell appops set ... SCHEDULE_EXACT_ALARM ignore`): no settings redirect, app stays foregrounded, and the notification still delivers on schedule.

[A device reboot clears the OS's pending alarms, which could silently drop that day's notification if the app isn't reopened before 12:00] → Substantially mitigated by the catch-up window itself: recalculation re-runs on every app resume, and as long as the app is opened at any point before 20:00 local that day, the catch-up path recovers the notification even though the original 12:00 alarm was lost to the reboot. The only remaining loss is a day the app isn't opened at all before 20:00 after a reboot — a small UX gap, not a correctness bug (no stale or duplicate notifications result).

[Notification permission denied, silently, with no in-app indication] → Accepted as out of scope for this change; the setting still saves and the recalculation logic still runs (harmlessly, as a no-op past the permission check) so nothing breaks if the maker grants permission later — this can be revisited if it proves confusing in practice.

[Deleting a channel doesn't itself trigger a recalculation, so a scheduled notification's stored `extra.codes`/body text could reference a channel that was deleted moments later] → Not a new class of problem — `CouponDetailModal` already handles a coupon whose channel was deleted with a "no channel" fallback — and it self-heals at the next recalculation trigger (app resume, or the next coupon save) same as the reboot case above. Not worth a dedicated trigger for the rarity of that ordering.

[The plugin's `schedule.at` may reject or misbehave on a timestamp that is exactly "now" rather than genuinely in the future] → The catch-up path schedules a few seconds ahead (e.g. `now + 2s`) rather than `now` itself, which is indistinguishable from "immediately" to the maker but avoids relying on undefined behavior for a zero/negative-offset schedule. Verify the exact margin needed against the installed plugin version during implementation.

[Marking a code `delivered`/`pending` happens at scheduling time, not at confirmed delivery — if `LocalNotifications.schedule()` itself throws (e.g. permission revoked between the check and the call), a code could end up marked without anything actually having been scheduled] → Only mutate `deliveredCodes`/`pendingCodes` after the corresponding `schedule()` call resolves successfully, so a failed attempt leaves those coupons uncovered and a later recalculation that day (still within the window) gets another chance rather than being permanently locked out by a failure.

[The per-coupon lock (`deliveredCodes`) can only grow within a day — nothing ever removes a code from it before the daily reset, even if that coupon is later deleted] → Accepted: a deleted coupon can't re-qualify for anything (it no longer exists in `listCoupons()`'s results), so an orphaned entry in `deliveredCodes` is inert — it never affects any future bucket comparison, it just sits unused until the next day's reset clears it.

[Bucketing a qualifying coupon under every offset `0..k` (instead of just `k`) means the same coupon can appear in up to `warnDaysBefore + 1` separate `schedule()` payloads per recalculation, each recomputed from scratch] → Accepted: `warnDaysBefore` is capped at `20`, and a maker's coupon count is expected to be small (their own promo codes, not a catalog), so this stays cheap — the same reasoning already applied to fetching the full coupon table on every recalculation.

## Migration Plan

- Add `@capacitor/local-notifications` to `apps/mobile/package.json`; run `pnpm install`.
- Add `<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />` to `AndroidManifest.xml`.
- `pnpm --filter mobile run build` then `npx cap sync android` (as with any new native plugin — see CLAUDE.md's existing `@capacitor-community/sqlite` note) before the next Android build.
- No database migration and no data backfill — this change reads only existing, already-derived coupon fields.
- Rollback is simply reverting the change: no persisted data format is introduced that would need cleanup (the one new `localStorage` key, `couponkeeper.warnDaysBefore`, is inert if unread).
