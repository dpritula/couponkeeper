## Context

`CouponFormModal` today only creates (`couponsStore.create` → `createCoupon`, always an `INSERT`). `CouponDetailModal` is read-only. Both are plain `<Teleport to="body">` popups opened as siblings from `CodesPage`/`CalendarPage` via local `ref`s (`selectedCode`, `showForm`), not routes. `coupons.code` has a DB-level `uniqueIndex` (`coupons_code_unique`); channel is a separate many-to-many join (`coupon_channels`), so there is no single column to put a composite `(code, channel)` unique index on without denormalizing. Start/End are currently free-text inputs parsed by `parseDisplayDate` (`DD.MM.YYYY` → ISO), which throws on malformed input instead of failing validation gracefully. See proposal.md for the full motivation.

## Goals / Non-Goals

**Goals:**
- One shared form component for both create and edit, driven by a mode flag/prop, not a duplicate component.
- Validation that runs synchronously before touching storage, collects every problem at once, and renders them as one informative message.
- A reusable calendar-popup date picker for Start/End that can only ever produce a valid ISO date.
- Code+channel uniqueness enforced in application code, not a DB constraint, since channel isn't a column on `coupons`.

**Non-Goals:**
- Multi-channel coupons (the form still picks exactly one channel; the many-to-many schema already supports more, unchanged by this work).
- Editing usage count directly (it's not a form field in create mode either; edit leaves it untouched — see the `coupon-editing` spec).
- A generic reusable "field-level inline error" UI (per-field indicators). The spec calls for one combined message above Save, matching the existing `save-error` slot design language already used by `CouponFormModal`/`ChannelManagerModal`.
- Undo/versioning/audit trail for edits.

## Decisions

### 1. `CouponFormModal` gains a `mode: 'create' | 'edit'` (derived from an optional `coupon` prop), not a separate `CouponEditModal`
Passing `coupon: PromoCode | null` — `null`/absent means create, present means edit. The field refs (`code`, `channel`, etc.) are initialized from `props.coupon` once, in `setup()`; since `CouponFormModal` is rendered unconditionally by its parent (`CodesPage`/`CalendarPage`) with only an internal `v-if="open"` on its own template root, the component instance itself is never unmounted by that internal `v-if` — so those `ref()` initializers would only ever run once, on the very first mount, not on every subsequent open. **Correction found during implementation:** an earlier version of this decision proposed keying that internal root element on the coupon's code, expecting that to force a remount — it does not, because keying an element only affects patching of that vnode, not the enclosing component instance that owns `setup()`. The fix has to key the `<CouponFormModal>` tag itself, at the call site in `CodesPage`/`CalendarPage` (e.g. `:key="editingCode?.code ?? 'new'"`, with the create-mode case additionally distinguishing "closed" from "open" so two separate create-mode opens back to back also remount rather than reusing stale typed-in values) — that's what actually makes Vue tear down and recreate the instance, re-running `setup()` with the new `coupon` prop. This directly satisfies the proposal's "same form, not a separate edit form" requirement and reuses 100% of the existing markup/CSS.

Alternative considered: a fully separate `CouponEditModal.vue` copy-pasted from `CouponFormModal.vue`. Rejected — guaranteed drift between create/edit validation and styling over time, and the spec explicitly calls for one form.

### 2. Detail → edit transition is a local state swap in `CodesPage`/`CalendarPage`, not a new popup layered on top
Today `selectedCode` drives `CouponDetailModal` and `showForm` drives `CouponFormModal`, as two independent booleans. Add a third local state, `editingCode: PromoCode | null`. Activating the header edit icon in `CouponDetailModal` emits `edit`; the parent handles it by setting `selectedCode = null; editingCode = code`. `CouponFormModal`'s `open` becomes `editingCode !== null || showForm`, and its `coupon` prop is `editingCode`. On close (Save or ×), the parent resets whichever of `editingCode`/`showForm` was active. This keeps `CouponDetailModal` and `CouponFormModal` as independent, stateless-about-each-other components — the "replace the view with the form" behavior lives in the two page components, which already own this kind of popup orchestration (`CodesPage`/`CalendarPage` per CLAUDE.md's "Architecture and Data").

Alternative considered: `CouponDetailModal` internally rendering `CouponFormModal` when in an edit state. Rejected — would make the detail modal own creation/edit logic that isn't otherwise its concern, and breaks the "all popups are siblings of the page" pattern the rest of the app follows.

### 3. Code+channel uniqueness is an application-level check inside `createCoupon`/`updateCoupon`, and the DB's `coupons_code_unique` index is dropped
`coupon_channels` is a join table; `coupons` has no `channel_id` column, so a native composite unique index isn't available without denormalizing the schema (rejected — CLAUDE.md is explicit that the many-to-many model is deliberate, in place to support multi-channel coupons later). Instead, `queries/coupons.ts` gets a helper (e.g. `codeExistsOnChannel(code, channelKey, excludeCouponId?)`) that joins `coupons` → `coupon_channels` → `channels` filtered by code + channel key, used by both `createCoupon` and the new `updateCoupon` before writing. `excludeCouponId` lets edit exclude the row being saved from matching itself. Since this replaces the DB's own enforcement, `schema.ts` drops `uniqueIndex('coupons_code_unique')` (regenerate the migration via `db:generate` per CLAUDE.md); leaving both in place would make the old global-uniqueness index reject the now-legal "same code, different channel" case.

Alternative considered: keep the DB index and only add the softer app-level check for informative errors. Rejected — the DB index is *stricter* than the desired rule (it forbids same-code-different-channel, which the spec explicitly allows), so it must go, not just be supplemented.

### 4. Validation is a pure function returning a list of problems, called before any store/DB call
`CouponFormModal` gets a local `validate(): string[]` (or a small `utils/couponFormValidation.ts` if it needs to be unit-tested independently) that checks, in order: code non-empty, channel selected, discount type selected (always true given the segmented control's default, but checked for completeness), value non-empty, start date present, end date present, end >= start. Each failing check appends one `t()`-translated message. `save()` runs this first; if non-empty, joins the messages into the existing `errorMessage` ref and returns without calling `couponsStore.create`/`update`. The code+channel uniqueness check is async (needs a DB round-trip) and is therefore checked separately, after the synchronous checks pass, inside the try/catch around the actual save call — a thrown "duplicate" error from `createCoupon`/`updateCoupon` is caught and turned into its own informative message via the same `errorMessage` rendering, joined with any other problems that are still relevant. This keeps the fast, free client-side checks synchronous and cheap, while the one check that requires storage stays where storage errors are already handled.

### 5. New `DatePickerModal.vue`, reusing `utils/calendar.ts`'s existing `getMonthGrid`
A new Teleport-to-body popup, styled like `MonthYearPickerModal`/`CouponFormModal` (bottom-sheet, header + body), showing one month's day grid (from `getMonthGrid`) with prev/next month controls, opened by tapping the Start or End field. Selecting a day emits the chosen ISO date and closes the picker. `CouponFormModal` holds two booleans (`showStartPicker`/`showEndPicker`) instead of two free-text `<input>`s for the date fields; the fields themselves become read-only buttons displaying the currently chosen date (formatted via the existing `formatShortDate`). This reuses the pure grid logic that already backs Calendar instead of writing a second date-grid implementation, and guarantees every value is a real calendar date by construction (satisfying the spec's "picker cannot produce an invalid date" requirement) rather than validating a free-text input after the fact.

Alternative considered: native `<input type="date">`. Rejected per the earlier product decision — the app's own popup styling is preferred over a platform-controlled native picker, for visual consistency with the rest of the form.

### 6. `updateCoupon` looks up the coupon by its current code, updates all editable columns, and re-derives status/daysLeft the same way `createCoupon` does
Mirroring `createCoupon`'s shape: `updateCoupon(currentCode: string, input: NewCouponInput)` finds the row by `currentCode`, `db.update(coupons).set({...}).where(eq(coupons.id, row.id))` (code, discountType, value, startDate, endDate, usageLimit, note, plus freshly derived status/daysLeft — `usageCount` and `id` untouched), then replaces the single `coupon_channels` row for that coupon (delete existing join row(s), insert the new one) since the form only ever picks one channel. Looking up by the *old* code (not id) keeps the store's `update` action signature symmetrical with `remove(code)`, since `PromoCode` (the view-model) doesn't carry the DB's internal numeric id — the coupon's code, before editing, is a stable enough handle for the duration of a single save call.

### 7. `client.ts`'s `ensureSchema` is extended to apply migration 0001, including self-healing an existing db that predates it
**Found during implementation, not anticipated when this design was first written.** `client.ts` hardcoded importing only `migrations/0000_elite_snowbird.sql` and guarded running it on whether the `coupons` table already existed — there was no mechanism to apply a *second* migration at all, because this is the first schema change since the initial one that actually needed new SQL (the earlier `notStarted` status addition was a TS-only enum change). Left as-is, the new `0001_naive_meggan.sql` (dropping `coupons_code_unique`) would silently never run — confirmed by testing: even a freshly wiped dev database kept hitting `UNIQUE constraint failed: coupons.code` on a legitimate same-code-different-channel save, because `ensureSchema` never even looked at 0001, let alone applied it to a db that already had `coupons`.

Fixed by having `ensureSchema` import both migration files and, for a *fresh* db (no `coupons` table yet), run 0000 then 0001 in order. For a db that already has `coupons` (dev databases from before this change, and any real device that already has the app installed), there's no applied-migration version tracking to know whether 0001 has run — so instead of building one, `ensureSchema` checks `sqlite_master` directly for whether `coupons_code_unique` still exists; if it does, that db predates 0001 and gets it applied now. This self-heals both the already-tested dev case and the real-device upgrade case (a device with the app already installed) the same way, without a general-purpose migration runner.

Alternative considered: build proper migration-version tracking (e.g. SQLite's `PRAGMA user_version`) so `client.ts` discovers and applies any pending migration file automatically. Rejected for this change — more robust for *future* schema changes, but a materially larger addition than this change's own scope calls for; deferred until a change that actually needs more than one extra migration justifies it.

## Risks / Trade-offs

- **[Risk]** Dropping `coupons_code_unique` removes a safety net at the DB layer — a bug in the new app-level check could let two coupons with the same code+channel slip through. **Mitigation**: the same join-based check is shared by both `createCoupon` and `updateCoupon` (one implementation, not two), and the `coupon-editing` spec's scenarios (duplicate rejected, different-channel allowed, self-edit allowed) give concrete cases to verify against.
- **[Risk]** Keying the form's root on `coupon?.code` to force a reset when switching between create/edit or between two different coupons relies on the code being unique-*enough* to be a good Vue `:key` at any given moment; if a race let two opens overlap, this could misbehave. **Mitigation**: the form is a modal — only one instance is ever open at a time by construction (`open` is a single boolean per page).
- **[Trade-off]** The uniqueness check adds a DB round-trip on every save (create or edit) that wasn't there before for create (which previously relied on the DB constraint to reject a duplicate, surfacing as a generic thrown error). This is an accepted, small latency cost for a local SQLite query in exchange for an informative message instead of a raw constraint-violation error.
- **[Risk]** The `coupons_code_unique`-existence check (Decision 7) is itself a one-off, hand-rolled substitute for real migration tracking — it only knows how to detect *this specific* stale index, not any other kind of pending migration. **Mitigation**: scoped deliberately to just this change's need (see Decision 7's alternative-considered note); a future change needing more than this one extra migration should introduce real version tracking rather than stacking more one-off checks here.

## Migration Plan

1. Update `schema.ts` (drop `coupons_code_unique`), run `pnpm --filter mobile run db:generate` to produce the new migration, matching the existing pattern of one generated SQL file per schema change.
2. No data migration needed — dropping a unique index doesn't require touching existing rows, and no existing seeded data violates the new, looser rule.
3. Verify on the Android emulator per CLAUDE.md's native-vs-web-fallback guidance, since this change touches schema/migrations, which have already diverged between the two once (the `--> statement-breakpoint` splitting bug).

Rollback: revert the schema/migration change and the query-layer uniqueness check together; the app-level check and the DB index are alternatives, not layered, so there's no partial state to reconcile.
