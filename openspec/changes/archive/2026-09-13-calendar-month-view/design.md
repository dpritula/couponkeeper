## Context

See `proposal.md` for motivation and scope; see `specs/calendar-view/spec.md` for required behavior. This section covers only the current implementation shape that constrains the approach:

- `CalendarPage.vue` today: a hardcoded `DayCell[]` (3 weeks, fixed `dim`/`today`/`selected`/`marks`), a `monthLabel` computed once from the literal string `'2026-09-01'`, decorative `‹`/`›` spans with no click handlers, and `dayCodes` filtered from `mockPromoCodes` by two hardcoded `code === '...'` checks. None of this reacts to any state.
- `mockPromoCodes` (`data/promoCode.ts`) is the only remaining reader-free export once this change lands — `CodesPage`/`useCouponsStore` already read real data via `queries/coupons.ts`. Its `PromoCode` type (`channel: PromoCodeChannel | undefined`, ISO `startDate`/`endDate`, `status`/`daysLeft`) is what `CodeCard` and `CouponDetailModal` already render, so Calendar's real data must arrive in this same shape.
- `queries/coupons.ts`'s `listCoupons({ sortBy, sortDir, filter })` already supports `sortBy: 'daysLeft', sortDir: 'desc'` (implemented in `sortRowsInMemory` as `daysUntilEnd(endDate)` descending) and returns every coupon with its status/daysLeft already derived from the device-local date via `deriveCouponStatus` — this is exactly the ordering `calendar-view`'s "Default list order" requirement asks for, with no new sort logic needed.
- `useChannelsStore`/`listChannels()` already return the live channel list (`key`, `name`, `color`, `sortOrder`) that `coupon-channels` established; Calendar needs the same list for its legend, not a new query.
- The three existing Teleport-to-body overlays (`ConfirmDialog`, `CouponDetailModal`, `CouponFormModal`) and the newer `ChannelManagerModal` all share one structural pattern (fixed backdrop + bottom-sheet card, header/body/footer), per CLAUDE.md's explicit instruction to copy this shape for any new popup rather than inventing one.
- `sql.js` (the web dev fallback) can't run Drizzle's relational `with` queries or SQL-side date aggregation beyond simple comparisons (see CLAUDE.md gotchas); this design does all month-grid generation, per-day channel-overlap computation, and list filtering in JS over an already-fetched coupon array, not in SQL — consistent with how `sortRowsInMemory`/`attachChannels` already work.
- The maker's reference image marks a "star" over the legend/list area with a note about reusing Codes' filter component; cross-checked against `couponkeeper-ui-mockup.html`, no such element exists there. Initially confirmed with the maker as a screenshot annotation only (no filter/sort control). **Superseded by a later, explicit follow-up request** (with its own reference screenshot of the Codes toolbar) asking for the filter/sort controls to actually be added under Calendar's day-list heading — see Decision 7.
- `CodesPage.vue`'s `.app-header` (channel chips + sort/status/discount-type toolbar, see `coupon-list-filtering`) is defined entirely inline in that one file today — there is no existing shared/extracted component for it. Reusing it on Calendar means extracting it, not importing something that already exists.

## Goals / Non-Goals

**Goals:**
- Compute a real month grid (any year/month, correct weekday alignment, correct day counts including leap years) from a single `visibleMonth` state, with no hardcoded dates.
- Load all channels and all coupons once per Calendar visit (mirroring the unfiltered, small-scale, single-user dataset assumption `coupon-list-filtering`'s design already made for the Codes list), and derive day marks, the legend, and the selected-day list from that in memory.
- Reuse `CodeCard` and `CouponDetailModal` as-is; add exactly one new popup (month/year picker) following the established Teleport pattern.
- Keep Calendar's own selection/navigation state entirely local to `CalendarPage` (or a small composable it owns) — not layered onto `useCouponsStore`, whose `channelFilter`/`statusFilter`/`discountTypeFilter`/`sortBy`/`sortDir` belong to the Codes screen's own toolbar and must not be perturbed by visiting Calendar (and vice versa).

**Non-Goals:**
- The filter/sort toolbar (Decision 7) changes only which coupons appear in the selected-day list and their order — it does not change which days get channel indicator lines or which channels appear in the legend, both of which continue to reflect the full, unfiltered coupon set. A toolbar that also filtered the grid itself is explicitly out of scope for this change.
- Editing a coupon's dates from Calendar (e.g., drag to reschedule) — selection is read-only, same as the rest of this change's read-only list/detail flow.
- Pagination or virtualization of the coupon fetch — same small-dataset assumption the Codes list already relies on.
- Changing `queries/coupons.ts`'s SQL filtering/sorting surface — Calendar uses the existing `listCoupons({ sortBy: 'daysLeft', sortDir: 'desc' })` call unfiltered, doing its own date-range/channel derivation in JS afterward.

## Decisions

**1. Calendar owns its own local state, not `useCouponsStore`.**
`CalendarPage` calls `listCoupons({ sortBy: 'daysLeft', sortDir: 'desc' })` and `useChannelsStore().load()` directly (or via a small `useCalendarCoupons`-style composable), holding `visibleMonth`, `selectedDate`, and the fetched coupon/channel arrays as its own local `ref`s — not by writing into `useCouponsStore`'s `channelFilter`/`statusFilter`/`discountTypeFilter`/`sortBy`/`sortDir`. Reusing that store's *filtered* list would either leak whatever filter the maker last set on the Codes tab into Calendar's marks/list, or require resetting it on every Calendar visit and restoring it on the way back — both worse than just issuing Calendar's own unfiltered query.
*Alternative considered:* extend `useCouponsStore` with a second, Calendar-scoped list. Rejected as unnecessary indirection — Calendar's fetch is a single unfiltered `listCoupons` call with a fixed sort, not something other views need to react to, so a page-local composable is simpler than a new piece of shared store state.

**2. Month grid and per-day overlap are computed in JS from the full coupon array, not via a new SQL query.**
A small utility (e.g. `utils/calendar.ts`) takes `visibleMonth` and returns the ordered list of day cells (with `dim` for leading/trailing days), and a second function takes that day list plus the fetched coupons/channels and returns, per day, the ordered list of distinct channel colors to render as indicator lines (string comparison on ISO `YYYY-MM-DD`, which sorts and compares correctly lexicographically — no `Date` arithmetic needed for the inclusion check). This mirrors Decision 5 of the `coupon-list-filtering` design (JS-side derivation to stay consistent with `deriveCouponStatus`'s device-local "today", and to stay within what `sql.js` can run) and needs no schema or query changes.
*Alternative considered:* a dedicated `listCouponsOverlappingRange(start, end)` query. Rejected — with the existing small, unfiltered `listCoupons()` call already available and cheap at this data scale (same assumption the Codes list's design already accepted), a second query path duplicating `attachChannels`' channel-join logic isn't justified.

**3. A coupon contributes to one channel's line using only its first attached channel, matching how it's already rendered.**
`CodeCard`/`CouponDetailModal` already display a coupon via `PromoCode.channel` — a single resolved channel (`coupon.channels[0]`, per `stores/coupons.ts`'s `toViewModel`), even though the schema's `coupon_channels` join table is many-to-many. Day indicator lines use that same single channel per coupon, so a day's lines always agree with what the coupon's own card shows elsewhere in the app. If a coupon has no channel (its only channel was deleted), it contributes no line for that day but still appears in the selected-day list (same "no channel tag" handling `coupon-channels` already specifies for `CodeCard`).
*Alternative considered:* mark using every channel in `coupon.channels[]`. Rejected — the coupon-creation form only ever assigns one channel today, and marking by more channels than the coupon's own card shows would be visibly inconsistent for no current benefit; revisit only if multi-channel coupon creation is ever added.

**3a. Day indicator lines are thin, stacked horizontal bars inset from the top of the cell, not the current small round dots.**
Per the maker's follow-up refinement, `.marks`/`.m` (currently a horizontal row of 4px dots) is replaced with a vertical stack of thin (~2px-tall) horizontal lines, positioned with a small top inset from the cell's edge and a vertical gap between successive lines. The section 1 utility (design Decision 2) returns, per day, an ordered array of channel colors — ordered the same way `useChannelsStore().items` already orders channels (by `sortOrder`) — and `CalendarPage` renders one line per entry with `v-for`, in that order. **Superseded by Decision 3c below:** this first pass compacted the stack per-day (a channel absent that day contributed no element, so later channels' lines shifted up to fill the gap); the maker's next follow-up asked for a channel's line to hold a stable position across its whole week instead. This keeps the stacking order consistent with the legend below the grid (and with the channel filter/management order elsewhere in the app), so a maker who has learned "my top channel's color is always the first line, when present" can read it quickly across days.
*Layering with `.day.today`/`.day.sel`:* the lines render as an absolutely-positioned overlay inside `.day` (already `position: relative`), above the day number, and are unaffected by the border added for `.sel` since a border sits outside the padding box.
*Alternative considered:* keep the dot row (unchanged shape, just re-themed). Rejected — the maker explicitly asked for thin lines in place of dots, for a clearer per-channel read at a glance.

**3b. Lines run edge-to-edge (no horizontal inset) and gap increased, per a second follow-up refinement; the day number moves to the bottom of the cell.**
The first pass (Decision 3a) gave each line a small horizontal inset (`left`/`right` padding) and a 2px gap, so adjacent cells' same-position lines were visibly separated by the combined double inset. The maker asked for the lines to run the full width of the day cell and visually "fuse" into their neighbors' — since `.cal-days` already has no `column-gap` (cells sit flush against each other, per the original mockup grid), setting each `.chan-line`'s inset to `0` makes same-height lines in adjacent cells touch with no gap, reading as one continuous bar across the row wherever consecutive days share a color at that position. The vertical `gap` between stacked lines within one cell is increased (2px → 4px) for better separation between different channels' lines. The day number is moved from vertically centered to bottom-anchored (`align-items: flex-end` on `.day`, which only has the number as a flex child since the lines are an absolute overlay) with a small bottom padding, so it reads clearly below the line stack instead of overlapping the visual "weight" of the lines near the top.
*Why this doesn't need a spec change:* `specs/calendar-view/spec.md`'s "Per-day channel indicator lines" requirement already says lines are "inset a small amount from the top" and "stacked... with a small gap between each" without mandating a horizontal inset or exact gap size — both are implementation-level visual details the requirement's normative text already accommodates.

**3c. A channel's line holds a stable stacking position across its whole calendar week — supersedes Decision 3a's per-day compaction.**
Per a further maker follow-up: with 3a's per-day compaction, a channel dropping out mid-week (its coupon ending) caused every *other* active channel's line to visibly jump up/down on the next day, as the stack recompacted around the now-missing entry — distracting, and specifically called out as a bug to fix (this **is** a spec change: the "Per-day channel indicator lines" requirement's "remaining lines stack together without leaving a gap" clause is replaced with "every channel active anywhere in the week keeps the same position all week, blank on days it has no coupon"). `getDayChannelLines` (`utils/calendar.ts`) now groups `days` into consecutive 7-day chunks (matching `getMonthGrid`'s week rows) and, per week, first computes the *set* of channels active on any day in that week (ordered by `sortOrder`, same as before) — call this the week's channel order — then, per day in that week, returns one slot per entry in the week's channel order: that channel's color if it has an active coupon on this specific day, `null` otherwise. `CalendarPage` renders one `.chan-line` per slot unconditionally (a `null` slot binds `background: 'transparent'` — an invisible line taking up the same height and stacking `gap` as a colored one; TypeScript's `StyleValue` typing doesn't accept `null` as a per-property value here, so `null` is coerced to the literal string rather than relying on Vue's runtime property-removal behavior). A day with zero active channels still has no entry in the map at all (unchanged from 3a — no lines render for a fully inactive day).
*Alternative considered:* keep per-day compaction but only within the currently-selected week (e.g. re-anchor positions when a channel first appears). Rejected as more complex for no benefit — computing the week's full channel set upfront and rendering blanks is simpler and matches the maker's literal ask ("не должны смещаться до конца недели" — must not shift until the end of the week).
*Scope boundary:* stability holds only *within* one calendar week (row) — a channel dropping out at a week boundary does not need to reserve a position in the following week, since each week's channel-order set is computed independently. This matches the maker's own framing ("до конца недели" — until the end of the week) and keeps a lightly-used channel from permanently reserving a blank line in weeks where nothing of its ever appears.

**6a. Today's fill color moves from `--ck-ink` to `--ck-sage`, and the selected black ring is no longer suppressed when a day is both today and selected.**
Per the maker's follow-up, stark near-black (`--ck-ink`, `#1f2a24` in light mode) read as too harsh for "today" against the rest of the app's warm palette; `--ck-sage` — the app's primary accent color, already used for "active" state everywhere else (filter chips, the FAB, badges) — reads as "highlighted" while staying in the theme's established dark-toned vocabulary, per the maker's "more matching the theme's dark colors" framing. Text on the filled cell switches from `--ck-paper` to `#fff` for contrast against sage (matching `CodeCard`'s `.badge-active`/chip "on" states, which already pair sage backgrounds with white text). Because the fill is no longer near-black, the black selected-ring (Decision 6) is no longer visually redundant on top of it, so `.cal-days .day.today.sel` no longer suppresses the border — both styles apply together (sage fill + black ring) when today is also the selected day, matching how every other selected day already looks (a black ring), just with today's sage fill showing through the middle.
*Supersedes:* the second half of Decision 6 (the `.today.sel` border-suppression rule and its rationale) — kept here as 6a rather than rewriting Decision 6 in place, so the "why" of the original black-ring color change (§6) still stands on its own.

**4. The month/year picker is a new Teleport-to-body bottom-sheet popup, structured like `ChannelManagerModal`'s header/body/footer split.**
Header: title + close button (existing pattern). Body: a scrollable year selector (e.g. a horizontally or vertically scrollable list centered on the currently visible year) above a fixed 12-month grid (Jan–Dec) for the selected year, each month tappable. No footer/save button is needed — tapping a month immediately confirms the choice and closes the popup (there's nothing to "save" separately, unlike the channel form). This keeps to the one popup pattern already established rather than introducing a native `<ion-picker>` wheel, which would look inconsistent with every other in-app popup.
*Alternative considered:* Ionic's built-in `ion-picker` (native wheel-style month/year picker). Rejected — visually inconsistent with the app's own bottom-sheet design language used everywhere else, per CLAUDE.md's explicit "copy this shape" instruction.

**5. Selecting a leading/trailing (dimmed) day cell navigates `visibleMonth`.**
Per spec, tapping a dimmed day from the adjacent month both selects it and moves `visibleMonth` to that day's month — so the grid re-renders showing that day no longer dimmed, with the selection visible in-month. This avoids the confusing alternative of a selected day rendered dimmed/out-of-grid.

**6. Selected-day border color moves from `--ck-sage` to `--ck-ink`, and "today ∩ selected" keeps the existing filled `today` style.**
The reference image shows the selected day with a black ring; `CalendarPage`'s `.cal-days .day.sel` rule changes from `border: 1.5px solid var(--ck-sage)` to `border: 1.5px solid var(--ck-ink)`. When a day is both `today` and `selected` (the default state on first load), the existing filled `background: var(--ck-ink); color: var(--ck-paper)` "today" treatment is kept as-is and the selected border is not layered on top of it — a black-on-black-fill border wouldn't read as an additional signal, and the filled style alone already unambiguously marks that day as both "today" and "the currently selected day" the moment the screen opens.
*Alternative considered:* a lighter-colored ring around the filled today cell to signal "also selected". Rejected as unnecessary complexity for a state (today ≠ selected) that only diverges once the maker taps a different day, at which point the two styles (filled ink for today, black-ring for selected) are already visually distinct on two different cells.

**7. The Codes toolbar (channel chips + status/discount-type chips + sort dropdown) is extracted into a new shared `CouponFilterToolbar.vue`, reused by both `CodesPage` and `CalendarPage`, each bound to their own state.**
Per the maker's follow-up (with a reference screenshot of the Codes toolbar), Calendar's selected-day list gets the same filter/sort surface `coupon-list-filtering` already specified for Codes — channel filter, multi-select status filter, multi-select discount-type filter, and the sort dropdown (Start/End Date, Expiring Soon, Alphabetical, Times Used, Days Left, each ASC/DESC). Rather than duplicating that markup, `CodesPage.vue`'s inline `.chip-row`/`.toolbar` block is extracted into `components/CouponFilterToolbar.vue`, a presentational component: props for `channels`, `channelFilter`, `statusFilter`, `discountTypeFilter`, `sortBy`, `sortDir`; emits for each control's change. It does not read any store itself — `CodesPage` binds it to `useCouponsStore`'s existing state (unchanged behavior, just relocated markup), and `CalendarPage` binds it to a **new set of local refs** (`dayListChannelFilter`, `dayListStatusFilter`, `dayListDiscountTypeFilter`, `dayListSortBy`, `dayListSortDir`), consistent with Decision 1 — Calendar still never touches `useCouponsStore`. The component's own "manage channels" `+` button is left in `CodesPage.vue` rather than pulled into the shared component, since channel management is a Codes-only concern (per `coupon-channels`) and the maker's reference image for Calendar doesn't show it.
Filtering/sorting logic is applied where the day-list is already derived: `CalendarPage`'s `getCouponsForDate` result (design Decision 2 / `utils/calendar.ts`) is additionally filtered by `dayListChannelFilter`/`dayListStatusFilter`/`dayListDiscountTypeFilter` and, when a sort other than the default is chosen, re-sorted by `dayListSortBy`/`dayListSortDir` using the same in-memory comparators `queries/coupons.ts`'s `sortRowsInMemory` already uses for non-SQL sort fields (`daysLeft`, `expiringSoon`) — reimplemented locally in `utils/calendar.ts` rather than imported, since `sortRowsInMemory` operates on `CouponWithChannels` rows, not the `PromoCode` view-model Calendar already works with. Per the Non-Goals update above, none of this touches `dayChannelLines` or the legend — both keep deriving from the full unfiltered `coupons` array, so the grid always shows the complete picture even while the list below is narrowed.
*Alternative considered:* give `CalendarPage` its own independent filter/sort UI, hand-built rather than extracted from `CodesPage`. Rejected — the maker explicitly asked to reuse the Codes component, and a shared component also means a future change to the toolbar's look only has to happen once.
*Alternative considered:* let the toolbar filter the whole month (marks + legend), not just the list. Rejected per the maker's own framing ("фильтров/сортировок текущего списка" — filters/sorts of the *current list*) and the updated Non-Goals above; the grid stays an unfiltered overview.

**8. A third follow-up pass: square cell corners, a selection indicator that never shifts the lines inside, a lighter selected-ring color, an even lighter today fill, and thicker lines.**
Per the maker's third round of feedback (with an annotated screenshot pointing at the selected day):
- `.cal-days .day`'s `border-radius` changes from `10px` to `0` — square corners on every day cell, selected or not.
- The selected-ring's color moves from `--ck-ink` to `--ck-muted` — visible but lighter than stark black/ink.
- Today's fill moves from a solid `--ck-sage` (Decision 6a) to `--ck-sage-dim` with `--ck-sage` text — the same pale-tint-plus-accent-text pairing `CodeCard`'s "Active" badge already uses elsewhere in the app, read as lighter still than a full-strength sage fill.
- `.chan-line`'s height increases from 2px to 3px.
*Why square corners specifically:* the maker's annotation shows the selected day's ring rendering with rounded corners and asks for square ones instead; since the ring and the cell's own background share one `border-radius`, zeroing it applies uniformly to both, keeping them visually consistent with each other.
*No spec change needed:* none of `specs/calendar-view/spec.md`'s requirements mandate a corner radius, a specific border/fill shade, or an exact line thickness — all four are implementation-level visual details the existing "Selected-day visual indicator" and "Per-day channel indicator lines" requirements already leave open.

**8a. The selected-day indicator is an `outline`, not a `border` — superseding this decision's first draft.**
The first attempt at "selecting a day must not shift the lines inside it" (also raised in this same follow-up round) gave `.cal-days .day` an always-present `border: 1.5px solid transparent` with `box-sizing: border-box`, letting `.sel` only swap the color. That fixed the shift (confirmed: a selected cell's `.chan-lines` position is pixel-identical before/after), but broke something else it wasn't tested against: `position: absolute` children are positioned from the *padding* edge, and a border — even a transparent, zero-visual one — still insets that edge on *every* cell, not just the selected one. That reintroduced a ~3px gap between every pair of adjacent cells' lines, undoing the full-width edge-to-edge fusion from Decision 3b (caught by the maker in a follow-up screenshot). `outline` fixes both at once: it's drawn after layout, participates in neither the box model nor the padding edge, so it can never shift internal absolutely-positioned content and never insets `.chan-lines`' `left:0`/`right:0` on any cell. `outline-offset: -1.5px` draws it just inside the cell's edge, matching how the border used to look. `box-sizing: border-box` is no longer needed and is removed along with the border rule.
*Lesson:* when a fix targets one visual regression (the shift), re-verify the property it touches against every other requirement that property could plausibly affect (here, line edge-to-edge fusion) — not just the scenario the fix was written for.

## Risks / Trade-offs

- **[Risk]** Fetching all coupons unfiltered on every Calendar visit duplicates the fetch Codes already does, and could grow if a maker accumulates many coupons over time. → **Mitigation:** accepted, matching the same small-scale/local/single-user assumption `coupon-list-filtering`'s design already made for the equivalent Codes-list fetch; revisit only if this becomes an actual reported performance issue.
- **[Risk]** Computing "day has a mark" via ISO-string date comparison assumes both `startDate`/`endDate` and generated grid days are `YYYY-MM-DD` with no time component — a hidden timezone bug class if that assumption is ever broken elsewhere. → **Mitigation:** `PromoCode.startDate`/`endDate` are already plain ISO date strings end-to-end (per `parseDisplayDate`/`deriveCouponStatus`), and the grid utility generates the same `YYYY-MM-DD` shape locally rather than round-tripping through `Date` objects for the comparison itself.
- **[Risk]** A day with many distinct active channels could stack many thin lines and overflow the top of a small, square day cell if a maker creates many channels. → **Mitigation:** accepted as a v1 edge case (the mockup itself only ever shows up to 2 marks per day, and lines are only 2px tall with small gaps, so several fit before this becomes visible); not addressed by a cap or overflow indicator in this change.
- **[Risk]** Extracting `CodesPage`'s inline toolbar into `CouponFilterToolbar.vue` (Decision 7) touches a screen this change wasn't originally scoped to modify, risking a visual or behavioral regression on Codes. → **Mitigation:** the extraction is a pure relocation of existing markup/props behind a thin presentational component with no logic changes — `CodesPage`'s own filter/sort behavior (already covered by `coupon-list-filtering`'s spec) must render and behave identically before/after; verified in task 6's manual pass alongside the new Calendar toolbar.
- **[Risk]** Reimplementing `daysLeft`/`expiringSoon` in-memory sort comparators a second time in `utils/calendar.ts` (Decision 7), separate from `queries/coupons.ts`'s `sortRowsInMemory`, risks the two drifting out of sync if one is changed later without the other. → **Mitigation:** accepted for now since the two operate on different row shapes (`CouponWithChannels` vs `PromoCode`) and duplicating a small, stable comparator is simpler than adding a shape-agnostic abstraction for a single reuse site; flag for consolidation if a third caller appears.

## Migration Plan

No database schema or migration changes. Rollout is a normal code change, safely sequenced:
1. Add the month-grid/day-overlap utility (pure functions, independently testable against fixed inputs) — no UI change yet.
2. Add the month/year picker popup component, following the existing Teleport pattern.
3. Rewrite `CalendarPage.vue` to use the utility, the picker, live `listCoupons`/`useChannelsStore` data, and the updated selected-day border color — replacing `mockPromoCodes` usage entirely.
4. Verify on the Android emulator per CLAUDE.md's testing guidance (this only adds a new unfiltered `listCoupons` read pattern and JS-side date computation, not a new migration or SQL shape, so the known migration-splitting bug class doesn't apply — but the web/`jeep-sqlite` fallback and native SQLite should still both be exercised given this is a new read path over the full dataset).

Rollback is a plain revert; no data migration to unwind, and `mockPromoCodes`/its type are left in place (unused) rather than deleted, so reverting doesn't require restoring anything.
